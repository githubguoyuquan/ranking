# 话题动态指标方案

## 解决什么问题

新建话题不再固定显示 `streams`、`mentions`、`social`、`news`。系统会依据话题名称、榜单类型和语言地区生成 2–6 项适用于该话题的指标。业务类别、指标名称和权重都不写死在代码中。

`TopicKind` 现在只控制证据风格、数据覆盖率和时间衰减：客观榜偏可复核的直接数据，半客观榜允许多类证据互补，主观趋势榜强调近期变化。它不再把任何固定指标混入版本规则。

## 创建话题时发生什么

1. 运营填写完整话题名称、榜单类型、语言地区和实体数量。
2. API 将话题名称、`TopicKind` 和 `locale` 发送给 OpenAI；不发送租户、用户、实体、版本、排名或数据库记录。
3. 模型使用严格 JSON Schema 返回指标键、显示名称、解释、相对权重、是否必需、0–100 归一化口径和公开来源建议。
4. 服务端检查字段格式、指标键唯一性和权重有效性，再把权重归一化为合计 1。
5. 方案持久化在 `Topic.metricPlan`。刷新页面或稍后重新查询话题不会丢失。
6. 新建版本时，页面把方案复制到 `policyJson.weights`、`requiredSignalKeys` 和 `metricDefinitions`。之后该版本保持独立，不会被话题后续调整悄悄改写。

## 运营怎么操作

在“话题版本”页面创建话题后，逐项检查：

- 指标是否真正适用于该话题的所有参榜对象；
- 权重是否符合榜单定位；
- “必须有数据”是否只勾选不可缺少的指标；
- 展开的“数据口径与建议来源”是否可执行；
- 每个实体能否在相同时间窗、相同比较范围下得到 0–100 分。

可以在新建版本前调整权重和必需项。指标值本身仍通过实体指标写入流程采集或录入，`metricKey` 必须使用页面显示的英文键，`value` 必须按该指标说明换算到 0–100。系统只设计口径，不会根据名称虚构得分。

## 旧话题兼容

动态指标上线前的话题没有 `metricPlan`，页面会明确标记“旧规则”，并继续显示原版本已有的指标，确保历史榜单可解释。新话题如果没有配置 `OPENAI_API_KEY`，创建会明确失败，不会静默回退到固定四项指标。

部署新增迁移后执行：

```bash
npm run prisma:deploy
```

可用 `METRIC_PLANNING_MODEL` 单独指定支持严格 JSON Schema 的模型；未设置时沿用 `OPENAI_MODEL`，再默认 `gpt-4o-mini`。修改环境变量后需要按现有部署方式重启 API；本次代码变更不会自动替你重启进程。
