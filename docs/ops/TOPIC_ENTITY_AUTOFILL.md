# 话题实体自动填充：来源与操作方案

本次功能只负责寻找和保存参榜对象，不调整指标权重，不采集指标，也不自动跑榜。

当前修订已移除全部业务类别、国家、性别和专项筛选硬编码。配置 `OPENAI_API_KEY` 后，系统使用通用语义解析理解话题范围，再以 Wikidata 公开资料取数和核验候选；没有任何行业需要在代码中单独适配。

## 运营怎么使用

1. 打开“话题版本”的“新建话题”，填写榜单名称，并在名称中写清对象类别和必要限制。系统会理解完整名称，不使用业务类别词典。
2. 填写内部标识、榜单类型和语言地区，在“参榜对象数量”填写 1–50，默认 10。无需准备姓名、实体编号或来源地址。
3. 点击“新建并切换到该话题”。话题先保存，系统后台查找；在“新建版本”卡片的“参榜对象”中查看状态、实际数量和名单。
4. 点击对象旁的“查看来源”核对身份。找到足量对象后，新建版本的参榜对象会自动填入。
5. 不足指定数量时，点击“使用已找到的对象（N 个）”接受实际名单，或点击“重试自动填充”。失败时根据提示修正话题名称或稍后重试，无需重复创建话题。
6. 填写版本名称、生效时间和原有规则，创建版本；后续仍需补充真实指标才能计算榜单。

刷新页面或关闭浏览器不会删除服务器上的收集任务和结果。在下方“查询”区域填写该话题的内部标识，点击“版本列表”，即可重新加载名单继续操作。复制旧版本、手工修改编号或接受部分名单后，后台刷新不会覆盖已经选择的对象。

## 实体从哪里来

本版使用 Wikidata 公开结构化知识库。它提供稳定的对象编号（QID）、名称、简介、职业或类别等资料，通过公开查询接口可以按条件查找。[Wikidata 数据访问说明](https://www.wikidata.org/wiki/Wikidata:Data_access)、[查询接口说明](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service)。

获取过程：

- 将话题名称发送给 OpenAI，结构化解析为对象类别、通用成员关系和明确筛选条件；不能可靠表达的条件会使任务停止并提示，不会被静默删除。[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- 模型只返回查询计划中的名称，不得返回实体、编号、URL 或查询语句。类别、属性和值必须再由 Wikidata 名称或别名唯一精确匹配，才能组成受控查询。
- 通过知识库通用的“属于某类”“具有某职业”“子类”和已核验属性关系查询候选。程序没有预置任何业务类别编号或专用过滤条件。
- 优先选取在更多语言百科中有条目的候选，逐一检查名称和 QID、去重；再将话题名称和候选的 QID、名称、公开简介发送给 OpenAI，模型只能返回本批候选编号的子集，不能新增对象。
- 保存来源页面、对象说明和收集更新时间。这里的“有来源”说明身份记录可追溯，不等于来源的每一项信息均已独立审核。
- 在同一租户内按来源身份复用实体，并自动带入新版本选择；原有人工维护的姓名等字段保留。

按百科覆盖度选择只是通用候选收集策略，存在知名度和语言覆盖偏差，顺序不代表实力、成绩、人气或最终榜单排名。

## 支持范围和限制

不再有“内置支持的行业”清单。类别是否可用取决于外部知识库能否唯一匹配完整名称，以及是否存在可查询的成员关系；不承诺任何类别均可成功。

语义解析目前只接受能映射为 Wikidata 直接实体属性等值条件的限制。年份、赛季、现役、数值比较、否定、多跳关系等复杂条件会明确失败；需要这类范围时应后续接入相应权威名单来源，不能把条件丢掉后查宽泛名单。

模型和公开资料都可能遗漏或误判，候选必须由运营核对。语义核验不是业务事实的独立审计。人数不足时标记“部分”，不会编造对象。

同名但来源编号不同的对象不合并。以前手工创建且没有来源编号的实体不会仅凭同名被强制合并，仍可能出现同名记录。

## 已实现的任务和数据处理

- 创建话题接口接受可选整数 `entityCount`（1–50）；前端默认提交 10。旧接口调用不传数量时保持原有手工流程。
- PostgreSQL 的 `TopicEntityAutofill` 保存期望数量、queued/running/completed/partial/failed 状态、策略、说明、名单和更新时间。
- Redis/BullMQ 队列 `topic-entity-autofill` 后台执行，沿用项目现有 `PROCESS_ROLE=all/worker`。浏览器轮询状态；等待超过 3 分钟显示重试入口。
- 读取：`GET /v1/topics/:slug/entities`；重试：`POST /admin/topics/:slug/entities/retry`。读取按租户过滤，重试要求 admin 权限。
- 重试读取当前话题名称并生成新的任务令牌；旧任务不能覆盖较新的结果。失败重试会保留之前收集到的候选，但标明失败。
- `Entity.externalKey` 按“来源、租户、QID”唯一。实体和名单在同一事务内保存；需要搜索同步时同时写入 Outbox。
- 已有版本、冻结版本和历史快照不会被收集任务自动修改。
- 对外请求限于 Wikidata 和 OpenAI 固定接口；响应不超过 1 MiB，禁止跟随重定向，不访问模型或来源返回的任意链接。

## 发送到 OpenAI 的数据边界

发送内容仅有两类：第一次是话题名称；第二次是同一话题名称及 Wikidata 候选的 QID、名称、公开简介（每条简介最多 500 字符）。不发送租户、用户、内部标识、版本、指标、排名、数据库记录或鉴权信息。请求使用 `store: false` 和严格 JSON Schema；返回内容仍需本地格式检查、Wikidata 身份核验和候选集合校验。

## 本地部署与网络

新增迁移为 `20260908100000_topic_entity_autofill`，仅新增表、字段和索引。部署时运行：

```bash
npx prisma generate
npx prisma migrate deploy
```

随后重启 API 和执行排行任务的 worker，前端刷新即可。后台 worker 需要访问 Wikidata；若本机浏览器依靠代理才能上网，可配置 `ENTITY_DISCOVERY_HTTP_PROXY` 为可用的 HTTP(S) 代理。未配置时复用 `CRAWL_HTTP_PROXY`，两者都没有则直连；Node 服务不会自动读取 macOS 的系统代理设置。

本地开发环境已按当前系统代理配置为 `http://127.0.0.1:7890`。这是本机地址，不适用于容器；部署到其他环境需填写该环境可访问的代理，或使用直连。

在 `.env` 配置 `OPENAI_API_KEY` 后启用语义解析。可用 `ENTITY_DISCOVERY_MODEL` 单独指定支持严格 JSON Schema 的模型；未设置时沿用 `OPENAI_MODEL`，再默认 `gpt-4o-mini`。当前本机尚未配置密钥，因此运行时会明确降级为完整类别名称/别名精确匹配；不会假装已经理解自然语言。修改后需重启 API/worker。

## 后续来源扩展方案（本次未实施）

如果要做“某赛季现役 NBA 球员榜”，应新增相应赛事或联盟的官方/授权名单数据源，按赛季、队伍和注册状态收集，再用公开身份编号关联已有实体。品牌、产品等专业领域也应优先接入其权威目录或授权数据源。

每种新来源应满足：可稳定识别对象、明确覆盖范围和更新周期、保留来源链接/编号、可执行租户内去重；源数据不足时如实返回缺口。正式赛事名单的接入和指标采集属于后续功能，本版不宣称已经提供。
