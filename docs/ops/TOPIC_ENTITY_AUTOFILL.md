# 话题实体自动填充：来源与操作方案

实体自动填充只使用免费的 Wikidata 公开接口和项目内算法，不请求收费 AI，也不需要 API Key。程序没有足球、音乐、国家、性别等业务类别硬编码。

## 运营怎么使用

1. 在“新建话题”填写明确的对象类别名称，例如应写类别本身并可带“榜/排行榜”后缀。
2. 填写内部标识、榜单类型、语言地区和“参榜对象数量”。数量可为任意正整数。
3. 点击“新建并切换到该话题”。话题立即保存，后台任务随后查询 Wikidata。
4. 在“新建版本”区域等待名单出现，逐个点击“查看来源”核对身份。
5. 数量不足时，可接受已找到的对象，或修正话题名称后重试。
6. 确认实体和指标口径后创建版本；后续仍需录入真实指标值才能跑榜。

刷新页面不会删除任务。重新打开“话题版本”，按内部标识查询话题即可继续。

## 系统具体做什么

1. 项目内算法只清理“榜、排行榜、rankings”等展示后缀，保留完整类别名称。
2. 使用 Wikidata `wbsearchentities` 免费接口对类别名称或别名做唯一精确匹配。
3. 使用 Wikidata SPARQL 的通用“属于某类 / 具有某职业 / 子类”关系分批查询候选。
4. 在项目内校验 QID、名称、来源 URL 和重复项；不会用模型凭空补候选。
5. 按 100 条一批保存，直到达到运营指定数量或公开来源耗尽。

候选按百科覆盖度取回，顺序不代表最终名次。Wikidata 可能遗漏或分类不完整，运营必须复核。

## 当前限制

本地规则不会假装理解“现役、某赛季、某国、年龄小于”等复杂自然语言限制。若完整名称无法在 Wikidata 唯一匹配，任务会明确失败；此时应改用更清楚的类别名称，或后续接入对应机构的免费/授权公开名录。

同名但 QID 不同的对象不会合并。以前没有来源编号的手工实体也不会仅凭同名强制合并。

## 网络与部署

后台 worker 只需访问：

- `https://www.wikidata.org/w/api.php`
- `https://query.wikidata.org/sparql`

如需代理，设置 `ENTITY_DISCOVERY_HTTP_PROXY`；未设置时复用 `CRAWL_HTTP_PROXY`。修改代理后按现有方式重启 API 和 worker。项目不会读取或使用 `OPENAI_API_KEY`。
